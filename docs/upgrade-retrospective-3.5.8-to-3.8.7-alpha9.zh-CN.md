## 2. 先认清代码、镜像与生产现场

### 2.1 三种仓库身份不能混用

| 对象 | 本次作用 |
| --- | --- |
| `siyuan-note/siyuan` | 取得明确 tag 的官方源码 |
| `appdev/siyuan-unlock` | 既有解锁方案的背景与参考；不假设它已发布目标版本 |
| `JimEverest/siyuan-custom` | 本次实际维护的补丁、构建流程和部署证据仓库 |

真正的本地工作目录是 `E:\AI\siyuan-custom`。`E:\AI\Azure-obslinux` 保存 VM 运维资料，`E:\AI\SiyuanWrapper` 是另一个应用仓库；Wrapper 里可能有同名子目录或 gitlink，不能据此选错代码入口。

本仓库不是完整的上游源码 fork。基本工作流是：**取得固定上游提交 → 应用版本专属 patch → 测试与构建 → 发布候选镜像 → 验证镜像身份 → 部署**。因此，“更新版本号”本身并没有完成升级。

### 2.2 文档只能提供线索，现场证据决定部署参数

旧 `DEPLOYMENT.md` 曾使用 `siyuan` 容器名，将 `:6807` 作为主入口，给出 443 指向其他端口的整份 Caddy 示例，以及直接 pull `latest`、删除旧容器的更新方式。这套示例不能照抄到此次现网。本次使用原有 443 主入口，没有修改 Caddy；这不表示既有辅助 `:6807` 入口必须不存在或需要删除。

本次已核实的部署形态：

```text
浏览器 / Wrapper
        │
        ├─ 原有 HTTPS / Caddy 配置
        ▼
宿主机 127.0.0.1:6806
        ▼
容器 siyuan_custom
        ▼
/opt/siyuan/workspace → /siyuan/workspace
```

操作前应检查 Git remote、当前分支、未提交改动、VM 身份、真实容器参数、入口、运行版本和其他服务。不能用本地 HEAD、镜像 tag 或 VM 源码目录的 HEAD 代替实际运行镜像的证据。

以下是可供下一次调查使用的**只读命令示例**；容器名仍须先确认：

```bash
git status --short
git remote -v
git branch --show-current
docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
docker inspect --size --format '{{.Name}} {{.Image}} {{.State.Status}} {{.HostConfig.RestartPolicy.Name}}' siyuan_custom
docker inspect --format '{{json .Mounts}}' siyuan_custom
docker inspect --format '{{json .NetworkSettings.Ports}}' siyuan_custom
df -h /
free -h
```

完整 `docker inspect`、原始配置、日志和数据清单可能包含访问码、token、环境变量、存储地址或笔记文件名，应保存在 VM 私密目录，不直接输出到聊天或提交 Git。上述简化输出也应先确认符合当前环境的保密要求。

### 2.3 旧容器的 writable layer 是生产状态的一部分

升级前 `docker diff` 有 1,602 项变化，内核和前端资源存在运行时修改。旧基础镜像不足以表示完整现场；仅记录 `ttqwer1/siyuan-custom:latest` 会遗漏这些内容。

处理方法是同时保留旧停止容器和私密的容器层快照，再单独保护挂载工作区。容器层快照不包含 mounted workspace，也可能带有秘密，不能推送到公开 registry。`docker diff` 的全部变化也不应被自动解释为业务定制：需要区分程序修改、外观包和运行生成文件。

## 3. 关键方案与选择依据

| 选择 | 当时的依据 | 必须保留的约束 |
| --- | --- | --- |
| 从官方指定 tag 移植现有 patch | 不依赖 unlock 仓库恰好发布同版本，定制差异可审查 | 同时核对 tag 对应 commit 和 patch 内容 |
| 在 GitHub Actions 构建 | 生产 VM 只有约 2 CPU／4 GB RAM，OCR／ONNX 编译较重；本机 Docker 当时不可用 | CI 成功不等于 VM 已部署或数据迁移成功 |
| 使用唯一候选 tag 和 digest | 便于把实际产物与源码、patch、构建任务绑定 | 不靠浮动 `latest` 推断版本 |
| 一份独立完整工作区副本 | 当时约 7.48 GB 工作区、约 13.85 GB 空闲，不适合再造多份完整副本 | 无硬链接；停止写入后建立一致基线；保留至少 3 GiB 余量 |
| 隔离候选的出站网络并关闭同步 | 副本包含真实同步配置、设备身份和仓库密钥，可能写入同一个远端 | 网络隔离和配置关闭同时执行，不能只换本地端口 |
| 旧内核在候选验收期间停止 | 保证旧工作区不会在比较后继续产生新写入，便于确定回滚基线 | 这会产生维护停机；不是零停机方案 |
| 最后才恢复同步 | 公网访问和内容验收失败时，仍能恢复完整旧环境 | 同步可能写远端之后，禁止自动用旧本地工作区回退 |
| 给旧图标创建显式别名 | 上游会归一化旧图标名称，需要保留资源又避免被覆盖 | 除包名元数据外，资源字节不变；原包继续保留 |

本次方案的核心取舍是：接受受控的维护窗口，换取清晰的数据一致性和失败恢复路径。它不是滚动发布，也没有把同一个工作区交给两个内核并发运行。

### 4.1 固定源码、补丁和最终产物

本次身份链如下：

| 对象 | 身份 |
| --- | --- |
| 官方版本 | `v3.8.7-alpha.9` |
| 官方 commit | `def127fc774ab2b5ab9a0096609a15aa5ba30df4` |
| 镜像构建时 custom commit | `15ebf14380cbb0f5f009b38b54e3f9f9245c46ba` |
| 构建 run | `38162570597`，attempt 1 |

| 部署引用 | `ttqwer1/siyuan-custom@sha256:b722afa234debc64c2a9a3de2ae62001281212c31c26417132fefd7da7841b02` |
| source manifest SHA256 | `04c8e87aef738c3375f42ddc3d2baef0ed92c2f83749229ccc7a725cc7d51c15` |
| 实际验证平台 | `linux/amd64` |

后续补充运维脚本和本文的 commit 与镜像构建 commit 不同，这是正常情况。不能把“当前分支最新提交”反向写成已部署镜像的构建来源。

[prepare-source.sh](../scripts/prepare-source.sh) 检查版本格式、目的目录不存在、必需 patch 非空、tag 解析出的 SHA 与 release manifest 相等；应用每个补丁前先 `git apply --check`，并记录 patch SHA256、整体 diff SHA256、自定义仓库 revision 和工作树是否有未提交变化。新 patch 引入的文件通过 intent-to-add 纳入 diff。

在 Bash 环境中，以下命令可用于**构建准备**，不会升级 VM；源码目的目录必须是一个新的目录：

```bash
bash scripts/prepare-source.sh v3.8.7-alpha.9 /absolute/path/to/new-source-directory
bash build-docker.sh v3.8.7-alpha.9 ttqwer1
```

[build-docker.sh](../build-docker.sh) 在临时目录准备源码，用 `docker buildx build --load --platform linux/amd64` 构建本地候选，不自动 push，也不更新 `latest`。构建前仍应检查本机 Docker 可用性和资源。

本地构建脚本不会另外执行 CI 中的 API 契约检查和定向 Go 测试，不能把一次本地 Docker 构建说成与 CI 等价的验收。准备脚本默认使用 `python3`；Windows Git Bash 如仅提供 `python`，可通过 `PYTHON_BIN=python` 明确指定，仍需在 Bash 中运行这些命令。

对未来新版本，要先添加相应的版本目录和 `releases/<version>.json`，并审查该版本的必需补丁集合；不是只把命令参数换成另一个数字。当前脚本对 alpha.9 额外要求第五个构建补丁，这一条件也需随新版本重新判断。

### 4.2 四个业务补丁需要按“行为”移植

| 补丁 | 需要保留的行为 | 本次重点检查 |
| --- | --- | --- |
| [disable-update.patch](../patches/v3.8.7-alpha.9/disable-update.patch) | 禁用内置更新和自动下载，避免覆盖定制版本 | 更新 API 和下载设置都验证 |
| [default-config.patch](../patches/v3.8.7-alpha.9/default-config.patch) | 新工作区默认配置定制 | 不把新默认值强制写入已有用户配置；新版语言码为 `zh-CN` |
| [mock-vip-user.patch](../patches/v3.8.7-alpha.9/mock-vip-user.patch) | 无官方登录的本地账户／自托管功能行为 | 新配置结构、线程安全、持久化、后台云请求失败对本地账户和 S3 的影响 |
| [rename-endpoints.patch](../patches/v3.8.7-alpha.9/rename-endpoints.patch) | 三条上传路径和原授权语义 | 服务端路由、API 契约、生成代码、前端和插件调用一起变更 |

接口对应关系保持为：

```text
/upload             → /u_OCR
/api/file/putFile    → /api/file/p_ocr
/api/asset/upload    → /api/asset/ass_ocr
```

这些是上传接口改名，`/u_OCR` 的名称不代表它就是新版内置 OCR 识别接口。上传行为与原生 OCR worker 的推理验证在本次验收中分别处理。

新版使用分节配置和更多 API 契约代码，旧 diff 能否应用只是第一关。必须检查真实调用链：如果只改后端路由，前端、插件或 Wrapper 仍可能请求旧地址；如果只保证成功响应，却丢失 admin、只读或鉴权约束，也不算保留了原行为。

生成代码应与契约同步，执行 `go run ./apicontract/cmd/apigen --check`。本次 CI 的定向测试命令、Go tags 和测试选择以 [release-docker.yml](../.github/workflows/release-docker.yml) 为准，不能把这些定向检查说成所有上游测试均已运行。

本地账户移植不只是返回一个模拟用户：它沿用账户加密持久化机制，让已存在的本地账户缓存读取不等待同步锁；后台刷新对该本地账户直接返回，官方云请求的 401 处理也不能把它清除。回归测试覆盖重载、同步期间读取、刷新和云请求失败路径。真正的官方请求仍可能失败；这些保护不会让官方云认证自动成功。管理员预检仍然保留，非管理员不应因此取得或创建账户数据。

### 4.3 Docker／OCR 构建问题及定位方式

最终新增 [docker-build.patch](../patches/v3.8.7-alpha.9/docker-build.patch)。本次经历了三轮失败构建后取得成功；不同构建阶段的问题逐步暴露，不能看到最外层 `exit code 1` 就盲目重跑。

| 症状／失败位置 | 根因 | 处理及边界 |
| --- | --- | --- |
| 前端容器构建缺少农历 JSON | Docker 构建阶段没有复制前端依赖的共享资源 | 把所需共享文件纳入对应构建阶段，保留完整前端构建验证 |
| ONNX 依赖配置／构建失败 | Eigen 依赖构建需要 `patch` 可执行程序，基础构建环境缺失 | 显式安装构建依赖，不以跳过整个 OCR 阶段回避 |
| Alpine 上找不到 `execinfo.h` | glibc 诊断回溯代码与 musl 环境不兼容 | 对固定 ONNX 源码应用 Alpine 维护的 glibc 条件保护补丁 |
| 源码审查发现 ONNX 测试程序存在潜在 musl 数学函数签名兼容问题 | 原流程虽不运行测试，仍会编译相应测试目标 | 明确关闭这一共享库构建中不用的 ONNX 单元测试目标；应用测试与实际推理测试继续执行。这不是第三轮日志已经触发的另一个实际失败 |

### 4.4 发布与可追溯性的实际边界

工作流使用 repository secrets `DOCKER_HUB_USER`、`DOCKER_HUB_PWD`；后者作为 Docker Hub 登录凭据传入，名称不能凭旧文档猜成 `DOCKER_HUB_TOKEN`。仅凭变量名和登录成功不能判断其实际保存的是密码还是 access token。手动运行时选正确的升级分支；本次默认平台为 `linux/amd64`，没有验证 ARM64。

该 CI 实际执行 API 生成一致性和所选 Go 测试，然后完成 Docker 中的前端生产构建；工作流没有运行完整 `pnpm test` 或 `pnpm run typecheck`。不要将前端构建成功写成全部前端测试通过。构建 provenance artifact 配置保留 90 天，需要长期留存的信息应及时另行归档，而不是只留一个可能过期的 artifact 链接。

构建 artifact 与镜像 label 用于核对官方 SHA、patch 哈希和 manifest 哈希，再用不可变 digest 拉取部署。registry index digest、平台 manifest digest、Docker 本地 image ID 是不同概念；不能假设它们在每个 Docker 版本上都相等。

本次实现了**源码／补丁与已部署产物可追溯**。但基础镜像仍有浮动 tag，部分 GitHub Action 仍用版本 tag 或 `@main`，不能声称将来重建必然 bit-for-bit 相同。若需要该保证，应另行固定完整依赖链并验证。

此外，[auto-release.yml](../.github/workflows/auto-release.yml) 是尚未重构的旧逻辑：读取上游 master 的 package version、创建 release，并向 `master` dispatch 构建，且 release 的 prerelease 标记固定为 false。它没有执行本文的 VM 数据保护和验收流程。升级分支中的新构建保护也不能推定已经应用到 master；不要把此工作流当作安全的生产自动升级器。

<a id="data"></a>
## 5. 生产数据保护与隔离验证

### 5.1 备份必须包含什么

完整保留 `/opt/siyuan/workspace`，包括但不限于：

| 内容 | 为什么保留 |
| --- | --- |
| `data` | 笔记、附件、插件、用户外观资源等 |
| `conf` | API token、访问设置、同步配置、设备身份、AI 和编辑偏好等 |
| `repo` | 数据仓库、快照与同步相关记录 |
| `history` | 历史内容 |
| `temp`、数据库和 WAL | 名字像缓存并不代表本次可以删除；内含需要保护的运行数据 |
| 工作区其他内容 | 不能仅按已知目录做不完整白名单备份 |

### 5.2 一致副本和校验清单

先记录旧服务实际文档索引数，再禁用旧容器自动重启并干净停止它；确认没有其他写入者后，保存容器层快照和完整文件清单。复制工作区时使用独立文件，本次采用 `cp -a --reflink=never` 的方式，禁止通过硬链接节省空间。

“可以打开一个 tar”或“两个目录大小相同”不足以证明复制正确。清单应记录文件类型、内容 SHA256、大小、mode、uid/gid、mtime_ns，以及符号链接目标；首轮启动前比较原工作区和副本。检查路径类型、目的地不存在、符号链接边界和文件系统关系，避免覆盖或复制到错误位置。

本次 manifest 没有独立枚举验证 ACL／xattr，不应将结果扩大为所有文件系统属性均已验证。`cp -a` 的保留能力与验收实际覆盖范围是两件事。

候选在自己的目录中迁移；原工作区在验收期间保持旧版本状态。测试成功后，先将原目录改名到保护目录，再把候选目录改名为正式目录。**每次同文件系统 rename 各自原子，但两个 rename 不是一个事务**，因此每一步都要保存状态，并处理在两步之间失败的情况。

### 5.3 本次目录布局

```text
首次隔离验收期间：
  /opt/siyuan/workspace                     旧原件；旧内核停止
  /opt/siyuan/workspace-alpha9-candidate    独立副本；新内核迁移

成功切换之后：
  /opt/siyuan/workspace                     新版生产工作区
  /home/nl/siyuan-upgrade-20261012-alpha9/
      workspace-before                     完整旧原件
      attempt-1/、attempt-2/、attempt-3/      前轮证据及保留材料
      deployment-state.json                当前阶段与身份
      其余私密配置、清单、日志和证据
```

私密 stage 目录权限为 `0700`，新生成的私密证据和配置 JSON 按 `0600` 管理；完整原工作区、归档配置和外观包则通过 `cp -a`／rename 保留原权限和所有权，由外层 stage 保护。不要递归 chmod 为 `0600`，那会破坏原清单或目录可访问性。最终原件 manifest 仍准确匹配 25,456 个文件。该备份与生产位于同一 VM，不是离机备份；本次没有执行把完整旧环境恢复到另一台机器的演练。

### 5.4 不能让副本对外同步

复制的工作区包含真实的 S3 凭据、仓库密钥与设备 ID。如果只修改 HTTP 端口，新旧两个内核仍可能操作同一个远端仓库。

本次候选在启动前关闭 `sync.enabled`，如果存在 LAN sync 设置也关闭其 enabled，并接入 Docker internal network。候选配置和运行时 API 均再次确认同步关闭；直到正式入口验收完成才恢复原设置。

特别注意：LAN sync 原来为开启、未来版本新增后台写入通道、插件定时任务或不同存储 provider 时，需要扩大隔离和恢复设计。本次 `finalize` 对原 LAN sync 已开启的情况会拒绝继续，而不是自动处理所有环境。

<a id="pitfalls"></a>
## 6. 实际踩坑记录

### 6.1 配置格式错误可能让后续配置段没有加载

**表现：** 新内核能启动、笔记文件哈希正确，但图标和部分设置与原配置不同。进一步核对发现，影响不限于外观，还涉及存储配置、仓库 key、快捷键、UI layout 和 AI 配置。

**根因：** 旧版 `appearance.icons` 是字符串数组，新版解码为具名对象数组。新的分节配置解码在遇到不兼容值时返回错误，可能使后续配置没有按原值加载。随后保存的候选配置已经包含默认值／缺失值，不能视为可信的迁移输入。

**修复：** 停止候选，先完整保留失败的候选 `conf`，再从受保护的旧原件恢复整个 `conf` 目录，包括原配置版本；在启动前只清除已确认过时的外观派生缓存，让正常上游迁移重新执行。不能只修改一个 icon selector，更不能以失败配置为基础逐项猜测补回。

**以后怎么查：** 同时比较磁盘配置和认证后的运行时 `getConf`。把 API token、repo key、system.id、UI layout、完整原有同步参数及 AI 语义纳入独立检查；HTTP 200 和版本号只能证明服务在响应。

### 6.2 旧图标包存在，选择仍可能被上游改写

**根因：** alpha.9 的 `NormalizeAppearance` 会把名为 `ant` 或 `material` 的选择归一化为 `litheness`，即使原包已经复制到用户目录。

**修复：** 保留原包，额外生成 `legacy-ant` 和 `legacy-material`。目录名必须与 `icon.json.name` 相同；只允许这个 metadata name 变化，`icon.js` 和其他资源 SHA256 保持原样，其他 metadata 值相同。已有同名包不允许静默覆盖。

**验收：** 检查源包、别名包、保存的选择、运行时可用列表和所有原有外观偏好。最终选择是 `legacy-material`，主题仍为 `daylight`／`midnight`。单纯看到目录存在不等于前端实际采用了它。

### 6.3 合理的上游迁移不能误判为“设置丢失”

本次允许的差异都有固定源码依据：

- 原语言 `en_US` 变为 `en`；语言使用上游明确映射，不是简单替换下划线。新建工作区默认 `zh-CN` 不应覆盖用户原本的英文设置。
- 历史 graph 默认 `maxBlocks=10240` 归一化为 `16384`；其他正数自定义值不能被随意重置。
- 原 `ai.openAI` 迁移到 provider、model 和不同场景设置，验证 endpoint、凭据、模型及参数的实际语义，不仅比较字段名。
- 图标／主题列表和版本字段属于派生缓存；原用户选择和偏好仍需验证。

如果某个差异找不到源码解释，应停止并调查；不能因为“这是新版本”就把整个配置段加入忽略名单。

### 6.4 同步锁时间戳变化不等于笔记发生改变

一次失败恢复后，旧服务重新运行并同步，导致 `repo/lock-sync` 中的时间戳更新。下一轮复用候选时，严格的持久化数据比较据此拒绝继续。

确认 DejaVu 的写入逻辑后，处理被限定为：两边都必须是普通文件，JSON 恰好只有 `deviceID` 和 `time`，设备 ID 与原配置一致，时间为正整数。先归档候选的锁记录，再从**新一轮已经停止的原件**复制最新记录，保留所有权并核对 SHA256。

这不是忽略整个 `repo`，也不是删除同步锁。其他任何未解释的新增、删除或字节差异仍会使复用失败。

### 6.5 Docker internal network 下发布端口不一定可达

在本机 Docker 行为中，候选使用 internal network 后，即使创建时指定了 `127.0.0.1:16806:6806`，实际发布端口仍为空。不能把超时马上归因于内核未启动，更不能为了方便测试给候选接上可出站网络。

处理是检查候选 ID、镜像、网络 internal 属性和实际 bridge IP，在宿主机运行一个**只绑定 loopback** 的 TCP 代理，转发到候选 IP 的 6806。重启候选后必须重新核对地址；测试结束按已记录 PID、命令行及容器身份核对后关闭代理。本次 16806 代理已关闭。

这是该次现场的具体行为，不能扩展为所有 Docker 环境都会忽略 internal network 的端口映射。

### 6.6 Docker commit 的标准输出不能直接当镜像 ID

本次 Docker 会在 commit 输出中混入弃用提示；把整段 stdout 写进 `snapshot_id` 会污染状态记录。处理方式是先确认 commit 成功，再通过结构化 `docker image inspect <快照标签>` 取得 `Id`。新增回归测试覆盖了带提示输出和 commit 失败的情况。

经验是：机器身份字段应来自结构化结果，并验证格式和目标对象；不要依赖命令恰好只打印一行。

### 6.7 服务响应版本，不代表工作区已经加载完

新版本可能先接受版本查询，再加载笔记本或建立索引。本次等待逻辑增加了 boot progress 完成和真实笔记本可读两个条件，准备 runner 的就绪超时为 900 秒。

轮询应有截止时间，输出阶段和必要诊断，不能无期限等待。1,858 个文件和 1,840 条索引记录也不能混为同一个数量；索引验收应使用旧内核实际查询得到的基线。

### 6.8 上传验收也可能误伤真实附件

附件上传可能按内容去重。重复使用同一张固定测试图，再按返回路径删除，可能误删工作区中早已存在的相同文件。

本次 `/api/file/p_ocr` 测试使用唯一文本文件，`/api/asset/ass_ocr` 和 `/u_OCR` 使用含随机差异的有效 PNG，再读取或下载并比较字节／哈希，只清理明确属于本次测试的合成文件。测试图片还必须是真正可解码的 PNG，否则失败可能来自输入无效，而不是接口回归。

浏览器测试不编辑真实笔记；恢复会话中的现有文档即可验证读取和渲染。本次实际没有触发“显式打开指定文档”的 fallback 路径。

### 6.9 系统 SQLite 缺少思源分词器，不能等同于数据库损坏

宿主机 Python 执行 `PRAGMA quick_check` 时出现精确错误 `no such tokenizer: siyuan`。思源使用的 SQLite fork 注册了自己的 FTS5 tokenizer，系统 SQLite 没有这个注册。

修复的是**验收分类**：仅当错误精确匹配，并且同一数据库的 schema 证明确实存在使用 `siyuan` tokenizer 的 FTS5 虚表（参数限已核实范围）时，记录为 `unsupported_custom_tokenizer`。其他 OperationalError、锁定、损坏、陌生 tokenizer 或非 `ok` 结果仍失败。

本次 1 个数据库实际通过 quick check，3 个列为工具不支持，0 个非明文数据库。不要写“4 个数据库完整性检查全部通过”，也不要因为 header 不像 SQLite 就自行断言文件是加密数据库或健康文件。应用自身 SQL／索引和文档 API 的通过是另一组证据。

### 6.10 OCR 构建成功还需要真实推理

原生 worker、动态库、模型路径或 ABI 仍可能在运行时失败，因此使用已知合成图片实际调用 worker。先用独立镜像容器验证：无工作区挂载、无网络、固定镜像 ID、仅写临时合成图片，设置内外超时、内存和 CPU 上限，并按随机所有权 label 验证后清理。

之后在正在运行的隔离候选中再做同样的实际推理。独立镜像探针耗时 1.94 秒；候选推理本身 0.382 秒，包含准备／清理的整次探针为 3.11 秒。前后内存采样不是峰值内存测量，不能当峰值报告。

早期独立运行的候选 OCR 检查曾与失败回滚发生重叠，清理时容器已停止。最终把候选 OCR 放在 runner 的数据检查之后串行执行，确保它完成前不会进入后续切换。不要让验收进程和回滚进程争用同一容器生命周期。

### 6.11 重试脚本和旧证据会造成第二类风险

第一次失败后已经有状态文件、候选容器、数据副本、快照和证据，重新调用“首次准备”不能当作恢复方案。也不能把旧轮通过的 JSON 留在原位，当作新轮通过。

本次通过双重执行锁、operation ID、精确 attempt guard、归档旧轮证据、刷新停机基线和新证据绑定来恢复。锁文件不能通过删除重建的方式“解锁”，否则不同进程可能锁住不同 inode。候选数据复用要双向比较原件与候选路径集合，不能只检查候选是否包含原有文件。

如果上一轮已回滚并让旧服务恢复运行，就必须重新采集当前基线；旧服务可能已产生合法的新写入。自动恢复只能处理当前操作确实拥有的容器和路径，不能因为启动失败就去停止别人的同名容器。

### 6.12 PowerShell、SSH 和模块位置也影响可执行性

本地环境是 Windows PowerShell，VM 是 Linux；Bash 的引号、变量、花括号扩展不能直接照搬。多行 JSON／PR 正文宜通过文件或结构化 API 传递，避免字符串插值和转义导致内容变形或秘密进入日志。

本次通过已核验主机密钥的 SSH 通道执行，使用 Paramiko `RejectPolicy`，没有用自动接受未知主机密钥掩盖连接问题。凭据仅用于当前授权操作，不进入代码仓库。

通过 stdin 运行 Python 适用于自包含脚本；依赖 `__file__` 相邻模块的脚本应先放到 VM 的私密目录，再从该目录执行。不要把 scratch 中的传输包装器误认为仓库已经提供的公开 CLI。

## 7. 成功切换的顺序与回滚边界

### 7.1 四轮准备的历史

| 准备轮次 | 实际阻断与处理 |
| --- | --- |
| 第 1 轮 | 外观验收拒绝；进一步发现完整配置解码问题，恢复旧服务，保留失败配置并准备兼容迁移 |
| 第 2 轮 | 持久化比较拒绝；确认旧服务恢复运行后更新了 `repo/lock-sync`，加入受限的最新原件复制规则 |
| 第 3 轮 | 配置身份、偏好及外观检查通过，宿主机 SQLite 的自定义 tokenizer 限制触发失败；恢复旧服务后修正验证分类 |
| 第 4 轮 | 新基线、配置迁移、数据／接口／Wrapper／OCR 和额外配置检查通过，随后提升生产并最终验收 |

失败的候选配置、诊断材料和原始数据都保留。本次最终一轮从停止旧服务到新生产就绪为 **4 分 29 秒**；前三轮另有维护窗口，这个数字不是全部累计停机时间。

### 7.2 最终成功的逻辑顺序

1. 核对固定镜像身份和源码／patch 证据，先完成不需要生产停机的构建及镜像探针。
2. 核对原服务状态、数据位置、空间和其他服务，采集旧索引基线。
3. 停止旧写入者，保留旧容器层和最新完整原件基线。
4. 创建／核验独立候选副本；恢复并兼容处理完整原配置，复制并验证旧外观资源。
5. 关闭候选同步和 LAN sync，在 internal network 启动，确保 loopback 测试入口可达。
6. 等待工作区真正就绪；测试版本、认证、定制接口、当前 Wrapper、原文件哈希、外观、数据库可验证部分及 OCR。
7. 重跑当前轮的配置身份与偏好检查，用 [complete-candidate-evidence.py](../ops/2026-10-12-alpha9/complete-candidate-evidence.py) 汇集新回执并绑定候选、镜像、原件 manifest。
8. 停止候选，重新确认原工作区仍精确匹配基线；按阶段改名保存旧原件，并把候选放回正式路径。
9. 保留旧停止容器，按原 inspect 的运行参数创建新生产容器，采用新版 `serve` 子命令；同步暂时保持关闭。
10. 在生产重新测试公网接口和实际 Wrapper；在浏览器之前再次验证配置身份和偏好，避免浏览器合法更新 UI layout 干扰启动迁移检查。
11. 新浏览器会话使用原访问码登录，验证已有文档渲染；随后再次验证所有原笔记／附件哈希、外观、其他服务。
12. 生产证据全部通过后，记录同步释放边界，再调用 `/api/sync/setSyncEnable` 恢复原开关。
13. 验证新版运行、同步设置、旧原件完整清单、旧容器／快照、其他服务和运行日志；关闭自有测试代理，保存报告。

### 7.3 状态机比一句“出错回滚”更重要

```text
preparing → old-stopped → candidate-created → prepared
                                               │
                  isolated acceptance + fresh receipts
                                               ▼
promoting → original-moved → candidate-moved → old-renamed
                                               ▼
production-created → promoted → production acceptance
                                               ▼
                                         sync-release
                                         /          \
                                  finalized     sync-release-failed
```

`prepare`／`promote` 中已经进入受保护变更阶段的失败，由驱动尝试恢复；准备 runner 对自己的验收失败执行恢复。不能据此推断任何独立命令失败都会自动回滚：例如 `verify-production.py` 是验证器，它本身不负责恢复。

**同步释放前：** 停止本次新容器，保留迁移后产生的工作区及新数据，恢复匹配原清单的旧原件和旧容器，验证旧版本。不能把旧内核直接指向新版迁移过的数据。

**同步释放时及之后：** 驱动在发送启用请求前就保存 `sync-release`。请求超时不能证明远端没有收到；一旦可能对远端写入，就阻止自动回退旧工作区。失败时尝试关闭新版同步，保留新版数据，调查并向前修复，或另行制定合并新旧本地／远端数据的恢复方案。

当前操作已经 `finalized` 并恢复同步。后续 Agent 不能直接执行本次的 `rollback`，也不能编辑状态文件把它伪装成尚未释放同步。

## 8. 验收矩阵与证据局限

| 层次 | 核验内容 | 单独通过仍不能证明什么 |
| --- | --- | --- |
| 源码／构建 | tag SHA、patch SHA、契约、定向测试、完整前后端和 OCR 构建 | 生产数据能正确迁移 |
| 镜像 | digest、平台、source labels、manifest 哈希 | 容器用了正确挂载与配置 |
| 运行 | 版本、boot progress、notebook API | 所有用户配置被保留 |
| 文件 | 原笔记／附件逐文件哈希；完整旧原件 manifest | 所有应用功能、所有数据库内部结构都正确 |
| 配置 | 保存值与 runtime；身份、存储、AI、编辑偏好和外观 | 每个外部 AI provider 都实际调用成功 |
| API／Wrapper | 原鉴权、合成数据上传／下载、旧路径状态、真实旧客户端 | 所有插件和所有客户端版本均兼容 |
| 浏览器 | 新会话认证、实际现有文档渲染、错误统计 | 所有编辑动作和 UI 功能均已覆盖 |
| OCR | 合成图片的实际 worker 推理 | 每一种 HTTP OCR provider、语言或真实图片都正确 |
| 同步 | 原设置恢复、观察到成功阶段、未见指定失败消息 | 第二台客户端参与的双向同步往返成功 |
| 恢复材料 | 原件哈希、旧容器、私密镜像都保留 | VM 整体丢失后的异机恢复已经演练 |

本次在 VM 上通过 **59 项运维回归测试**，覆盖目录切换失败恢复、同步释放边界、runner 所有权、配置／外观迁移、OCR 清理和 SQLite 错误分类等。它们与定向 Go 测试、API 契约检查、前端生产构建和真实部署验收属于不同层次，不应相加后称为“完整产品测试数量”。

公开证据只包含布尔值、计数、允许公开的版本／哈希／路径和合成数据结果。密码、访问码、S3 凭据、API key、笔记正文、原始 `getConf`、原始日志与完整私密 manifest 不进入 Git。

## 9. 脚本索引和使用限制

**不要把下面的索引理解为可直接复制执行的流水线。** 当时的传输、归档、轮次修复和部分人工检查也参与了成功部署。尤其要区分“某个 helper 已存在”和“首次 prepare 已自动调用它”。

| 文件 | 作用 | 下一次使用前必须知道 |
| --- | --- | --- |
| [deploy.py](../ops/2026-10-12-alpha9/deploy.py) | prepare／verify／promote／finalize／rollback 状态机 | 固定旧镜像、路径、容器及本轮身份；历史 `prepare` 尚未整合全部外观兼容处理和代理步骤 |
| [prepare-and-test.py](../ops/2026-10-12-alpha9/prepare-and-test.py) | 带锁和 operation ID 的首次准备 runner、就绪等待 | 不是最终一键流程；不会自动完成新增的 identity／settings／OCR 全套验证 |
| [resume-preparation.py](../ops/2026-10-12-alpha9/resume-preparation.py) | 第四轮受审查恢复路径 | 明确要求上一轮 attempt 为 3 且 rolled-back；不要为重跑而盲改 guard |
| [migrate-appearance.py](../ops/2026-10-12-alpha9/migrate-appearance.py) | 清除旧派生缓存、保真图标别名、偏好核验 helper | 调用者负责完整配置恢复、停机和关闭同步；不能当无副作用 CLI |
| [start-candidate-proxy.py](../ops/2026-10-12-alpha9/start-candidate-proxy.py) | 本次 internal network 的 loopback 代理 | 需要先检查实际网络行为和候选地址；固定命名和端口 |
| [smoke.py](../ops/2026-10-12-alpha9/smoke.py) | API、鉴权、上传、笔记本和索引验收 | 会写入并清理合成测试文件；依赖私密 index baseline |
| [wrapper-smoke.py](../ops/2026-10-12-alpha9/wrapper-smoke.py) | 当前 Wrapper 实际客户端兼容性 | 对象是当前部署镜像，不能用本地最新代码替代 |
| [verify-config-identity.py](../ops/2026-10-12-alpha9/verify-config-identity.py) | 原有身份、同步和 AI 迁移语义 | 设计用于同步释放前；默认候选端口，生产需要显式 workspace／port |
| [verify-settings.py](../ops/2026-10-12-alpha9/verify-settings.py) | 原偏好字段比较与允许迁移 | `--old`、`--new`、`--output` 指向当前轮，不接受旧回执代替 |
| [verify-appearance.py](../ops/2026-10-12-alpha9/verify-appearance.py) | 原包／别名 manifest 和实际选择 | 依赖相邻 helper 与本次私密证据 |
| [verify-data.py](../ops/2026-10-12-alpha9/verify-data.py) | 原内容哈希、候选身份、外观和 SQLite 分类 | 默认固定候选路径及 prepared 阶段；宿主机未支持不算通过 |
| [image-ocr-probe.py](../ops/2026-10-12-alpha9/image-ocr-probe.py) | 无挂载、无网络的固定镜像真实 OCR | 创建自有临时容器；严格身份和清理规则需保留 |
| [ocr-worker-smoke.py](../ops/2026-10-12-alpha9/ocr-worker-smoke.py) | 已运行隔离候选中的实际推理 | 要与容器生命周期变更串行，不能同时回滚 |
| [complete-candidate-evidence.py](../ops/2026-10-12-alpha9/complete-candidate-evidence.py) | 绑定本轮新 identity／settings／OCR 回执 | 其中数量门槛属于本次基线，未来需重建 |
| [browser-smoke-local.py](../ops/2026-10-12-alpha9/browser-smoke-local.py) | 操作者机器上的 Paramiko＋Playwright 验证 | 需要当前授权 SSH 认证；不要把密码写入命令示例、文档或提交 |
| [verify-production.py](../ops/2026-10-12-alpha9/verify-production.py) | 公网、浏览器证据、原内容和其他服务核对 | 只验证，不自动回滚；要先生成全部生产回执 |
| [verify-final.py](../ops/2026-10-12-alpha9/verify-final.py) | 同步恢复后的最终保护材料与运行检查 | 需要 finalized；不是整个远端同步往返测试 |
| [cleanup-proxy.py](../ops/2026-10-12-alpha9/cleanup-proxy.py) | 核验 PID／命令行后停止本次代理 | 只作用于本次拥有的进程，保留证据 |
| [collect-final.py](../ops/2026-10-12-alpha9/collect-final.py) | 收集可公开摘要 | 审核输出字段，不能扩成打印原配置／日志 |

`deploy.py` 的真实 CLI 接口为 `prepare --image ... [--operation-id ...] [--expected-version ...]`、`verify`、`promote --evidence ...`、`finalize --evidence ...`、`rollback`。这里仅记录接口，**不提供对当前 finalized 现场执行的命令**。即使某个参数可覆盖，脚本内部的其余固定断言也不会因此自动适配。

后续 Agent 应从这些代码中复用经过测试的机制，在新的运维目录准备适合新基线的完整流程，明确整合前置兼容迁移与所有验收；保留本目录作为历史审计材料。

## 11. 协作、凭据和过程管理经验

### 11.1 并行审查，串行改变生产生命周期

源码补丁审查、上游构建问题分析、运维恢复设计可以并行交给不同 Agent。明确文件所有权，避免多人同时修改同一部署脚本；生产容器的启动、停止、切换和回滚由一个执行者串行控制。

审查者应提供具体文件、函数或证据，而不是只说“没问题”。主执行者检查审查结论和实际 diff；Agent 完成消息不能替代真实测试输出。

### 11.2 凭据存在于历史聊天，不代表当前可用

建立连接前先检查当前可用的认证途径和主机指纹。确实缺少凭据时说明已经核实的缺口；用户已明确提供并授权后，按授权继续，不反复索取确认。

私密文件、传输凭据和公开文档分开管理。不要把密码硬编码到 helper、把 API 响应直接写进公开验收 JSON，或为了调试打开带秘密的 shell trace。错误日志也可能包含 endpoint 和文件名，应先脱敏。

### 11.3 让长时间工作可以交接

状态文件要回答：当前阶段是什么、哪个操作拥有它、正在使用哪张镜像、哪份原件基线有效、哪些证据属于本轮、同步是否可能已写远端。不能只靠聊天上下文或 PID 判断是否可恢复。

进度更新说明已经确认的事实和下一步检查，不反复播报没有变化的日志。构建／长任务用可恢复的执行记录，避免会话暂停后把“上次还在构建”误当成当前事实。恢复时先查实际状态和最终结果，再决定下一步。

### 11.4 多份运维资料不能整目录覆盖

此次 Azure 运维 skill 的 source 副本与 installed 副本包含不同的新旧 Coagen 记录。更新思源条目时，对每份做准确的局部修改并验证其他内容字节不变；不能把较旧 source 整目录复制回已更新的 installed 副本。

本指南保存在实际 `siyuan-custom` 仓库，并从 README／旧部署说明链接进入，降低下一位维护者只看到过时部署命令的可能性。
