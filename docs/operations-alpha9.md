# Azure SiYuan alpha.9 deployment procedure

For the detailed Chinese retrospective, decision rationale, actual failures and future-agent checklist, read [定制思源升级复盘与后续 Agent 操作指南](upgrade-retrospective-3.5.8-to-3.8.7-alpha9.zh-CN.md).

This procedure applies only to the audited Azure VM and the October 2026 migration. It is not a generic unattended updater. The deployment scripts refuse an unexpected original image, mount, port, restart policy, workspace layout or existing migration state.

The migration completed on 2026-10-12. Production started at 00:17:02 UTC and final acceptance passed at 00:19:50 UTC. The original S3 sync setting was restored only after public application acceptance, and a subsequent observation found one completed sync phase and no sync-data-repository failure. See [the deployment report](deployment-alpha9-20261012.md) and [sanitized evidence](deployment-alpha9-evidence.json). These results describe this deployment; the scripts are not safe to replay against its finalized state.

## Build identity

Build the official `v3.8.7-alpha.9` source at `def127fc774ab2b5ab9a0096609a15aa5ba30df4` using the four custom behavior patches and the Docker build corrections in `patches/v3.8.7-alpha.9`. These supply a shared frontend JSON file, install the patch executable used by ONNX dependencies, and apply Alpine's [glibc-guarded backtrace patch](https://raw.githubusercontent.com/alpinelinux/aports/3.23-stable/community/onnxruntime/no-execinfo.patch) to the pinned ONNX source. The shared-library build explicitly disables ONNX unit-test targets, which were already not run, to avoid the musl math-function signature incompatibility in those test sources. Application compatibility tests and deployment acceptance checks remain enabled. The workflow publishes a unique candidate tag and a source manifest. Deployment uses the resulting immutable registry digest, with the source revision and source-manifest digest checked against the image labels.

## Data and rollback protection

The production workspace is `/opt/siyuan/workspace`. Every part of it must be retained, including `conf`, `data`, `repo`, `history`, `temp`, database files and WAL files. Do not delete the latter directories as caches.

The private stage is `/home/nl/siyuan-upgrade-20261012-alpha9`, mode 0700. Original container inspection, configuration, file manifests and diagnostic logs belong only in this directory and must never be committed or published. The old container's writable layer is saved to a local private image; it may contain secrets and must not be pushed to a registry.

After a clean stop, copy the complete workspace to `/opt/siyuan/workspace-alpha9-candidate` without hard links. Check file bytes, permissions, ownership and modification times against the original manifest before first startup. The original workspace remains untouched during isolated testing. Copy old appearance packages removed from the new distribution into `data/icons` or `data/themes`, retaining any existing user package instead of replacing it. Verify the package bytes and the application's selected and available packages after startup.

The candidate remains on a Docker internal network. On this VM, Docker ignores the requested published port for that internal network, so `--publish 127.0.0.1:16806:6806` alone does not provide the test endpoint. Use a host-side TCP proxy bound only to `127.0.0.1:16806`, forwarding to the inspected candidate bridge IP on port 6806. Verify the candidate container and network identities, retain the internal network, and record the proxy process and destination in the private stage. Do not attach an external network to make the tests reachable. Recheck the destination if the container's address changes, and stop the recorded proxy when isolated testing is finished. Sync and LAN sync are disabled before startup. Do not test a second kernel against the production workspace or let a copied workspace write to real remote sync storage.

## Required appearance compatibility migration

Two separate alpha.9 compatibility changes require treatment before starting a candidate with the old configuration. First, the 3.5.8 `appearance.icons` cache is a string array, while alpha.9 decodes an array of named objects. The new `ConfSection.UnmarshalJSON` returns the decoding error before storing the appearance section; the error can also prevent later configuration sections from loading. Repairing only the icon selector after that startup is insufficient. With both workspaces protected and the candidate stopped, preserve the failed candidate configuration and restore the **entire original `conf` directory**, including the original configuration version, before applying the narrow sanitizer. `migrate-appearance.py:migrate_conf` removes the derived icon cache and removes legacy string-form theme caches if present; compatible object-form theme caches and every other original setting remain intact. Normal upstream migrations then run against the restored configuration. The caller disables sync and LAN sync separately for isolated testing.

This partial-decoding failure was observed during the first preparation attempt. Its effects extended beyond appearance to remote storage credentials, the repository key, keymaps, UI layout, AI configuration and other preferences. An HTTP version response or preserved note hashes cannot establish configuration fidelity. Keep the failed configuration privately for diagnosis; do not use it as the source of a repaired configuration or copy only selected fields back from the original.

Second, alpha.9's `NormalizeAppearance` rewrites selectors named `ant` or `material` to `litheness` on normalization, even when the old packages are installed. Preserve the old packages and install additional user-package aliases `ant → legacy-ant` and `material → legacy-material` under candidate `data/icons`. Each alias must have the matching directory name and `icon.json.name`, as `LoadIcons` requires those names to agree. Only this metadata name may change: `icon.js` and every other resource retain their original SHA256, and all other parsed metadata values remain equal. Existing packages are never silently overwritten. The currently selected `material` therefore becomes `legacy-material` while retaining its visual resources.

The helper verifies the existing candidate `ant` and `material` packages against the private original appearance backup before making aliases. Its `appearance-aliases.json` records source and target manifests, the exact two allowed mappings, original preferences, and container/image identities; the deployment state records that evidence file's SHA256. `verify-appearance.py` checks both manifests and the disk/runtime selections, retains original theme choices, and checks every original appearance preference except the explicitly regenerated `icons`, `lightThemes`, `darkThemes`, `themeVer`, `iconVer` and `themeJS` fields. It allows only documented upstream value migrations, including the exact legacy-language mapping from root `lang` to `appearance.lang` (for example `en_US → en`) and status-bar schema version normalization. A changed user preference, altered visual resource, unrecognized mapping, or unbound evidence file fails acceptance.

## Configuration fidelity and documented value migrations

Use the protected pre-startup configuration as the baseline for both preference and identity checks. `verify-settings.py` compares all pre-existing fields in the editor, file tree, export, keymap, search, graph, flashcard, tag, snippet, repository and OCR sections. Unexpected changes or missing fields fail; only individual transformations supported by the pinned source are accepted. New schema fields are reported separately. The compatibility changes relevant to this operation include:

| Original setting | Expected alpha.9 behavior | Verification boundary |
| --- | --- | --- |
| `lang: en_US` | Root `lang` becomes `en`; startup projects the migrated root language into `appearance.lang`. | Apply the exact `kernel/util/lang.go` legacy mapping, including `zh_CN → zh-CN`, rather than a general underscore replacement. |
| `appearance.icon: material` | Selector becomes `legacy-material`, with a matching alias directory and `icon.json.name`. | Preserve the original package and every visual resource byte; allow only the alias metadata name to change. `ant` has the corresponding `legacy-ant` mapping. |
| `graph.maxBlocks: 10240` | The historical default becomes `16384`. Values below `1` also become `16384`. | `kernel/conf/graph.go:NormalizeMaxBlocks` leaves other positive custom values unchanged. This permits no reset of local/global graph preferences. |
| Legacy `ai.openAI` configuration | Upstream migrates it into providers, models and scenario settings. | Verify the resulting endpoint, credential, model selection and parameters against the exact migration semantics; a new field layout is not permission to discard existing AI settings. |

`verify-config-identity.py` compares the API token, repository key, device `system.id`, complete UI layout and every original sync field in both persisted configuration and authenticated runtime `getConf`. Only sync `enabled`, `synced` and `stat` are excluded from equality; `enabled` must explicitly remain false during acceptance. It also checks the AI provider/model, editing, agent, embedding and MCP migration, including explicit defaults when the original AI section was empty. The administrator API response is held only in memory. Its evidence contains field booleans and counts, never credential, endpoint or configuration values. These checks must run again for the current attempt; earlier receipts do not establish the state of a later candidate.

## Promotion and sync release

After all isolated checks pass, stop the candidate and move the original workspace to the private stage's `workspace-before`. Move the validated candidate to the original production path, retain the stopped old container as `siyuan_custom_before_20261012_alpha9`, and create the new `siyuan_custom` using the original operational configuration and the new `serve` subcommand. Sync remains disabled through public HTTPS, authentication, browser, endpoint and Wrapper validation.

Only after production evidence passes, restore the original sync setting through `/api/sync/setSyncEnable`. The driver records this boundary before the request. Once remote writes may have occurred, an automatic rollback to the old local workspace is blocked: restoring local files alone cannot undo remote storage changes.

## Failure handling

Before sync release, rollback stops only this deployment's containers, preserves the migrated workspace and its new files, restores the untouched original workspace and old container, and checks the old version. No backup, old container, private image or failed workspace is deleted. Recovery tests exercise failures between directory renames and ensure the old kernel never opens migrated data.

The detached preparation runner uses an exclusive execution lock and an operation identifier. A duplicate invocation must fail without stopping or rolling back another run. A failed isolated test restores the old service only when the state belongs to the same runner.

The reviewed `resume-preparation.py` is recovery logic for the preserved candidate from this specific operation. It requires phase `rolled-back`, the explicit previous-attempt number guarded by that reviewed script revision, a stopped candidate with the expected image/mount/internal network, and both preparation and deployment locks. It must not be invoked as a general retry command or blindly rerun after another failure. Review each subsequent attempt against the actual state; do not bypass the attempt guard. Archive the preceding attempt's receipts and failed candidate configuration under the private stage before replacing any baseline or evidence; retain the lock inodes and bind fresh evidence to the new operation identifier.

Before candidate reuse, refresh the original index baseline, stop the old kernel cleanly with automatic restart disabled, and save a fresh private container snapshot and full original-workspace manifest. Compare the union of original and candidate paths in both directions for **every persistent tree outside `conf` and `temp`**, including `data`, `repo` and `history`, so additions, removals and changed content are detected. Explicit appearance-package additions require verified bytes. The only other reviewed difference is `repo/lock-sync`: DejaVu refreshes its timestamp during sync. Both versions must be regular JSON files containing exactly `deviceID` and positive integer `time`, with the same original device identity; archive the candidate record, copy the freshly stopped original record with its ownership, and verify its hash. Any other difference aborts reuse. Excluding `temp` from this reuse comparison is not permission to delete it: both workspaces and their complete contents remain retained. Preserve and replace the candidate `conf` as described above, regenerate aliases and evidence, and rerun all candidate acceptance checks. The old kernel remains stopped throughout that candidate test period; a failed attempt follows the protected rollback path.

The reviewed fourth preparation ran smoke, Wrapper, data/appearance and actual OCR inference checks. Identity and preference checks were then rerun separately for that same attempt. `complete-candidate-evidence.py` requires their fresh successful receipts, binds OCR to the current container/image, and adds their hashes to promotion evidence. After promotion, identity and preference checks ran again before opening the browser, so legitimate browser layout changes would not mask startup configuration loss.

## Acceptance evidence

- Exact authenticated version and immutable image/source identity.
- Readable notebook inventory and indexed documents.
- Every pre-existing note and attachment compared to its baseline SHA256.
- Three custom upload routes exercised with unique synthetic bytes, successful download/hash equality, cleanup, old-route absence and authentication checks.
- The currently deployed Wrapper's real client performs list, put/read and asset upload/read calls using its existing endpoint overrides.
- Fresh browser access-code login and an opened existing document render successfully.
- Selected icons and themes remain available; the selected legacy icon uses its explicit alias, the original material/ant packages retain their bytes, alias resources match their originals, and all original appearance preferences pass the compatibility checks above.
- API token, repository key, device identity, UI layout and existing remote storage settings remain equal, and the documented preference/AI migrations pass, without printing secrets.
- Unrelated container identities and public application health remain unchanged.

`verify-data.py` examines `temp/**/*.db` and opens files with the SQLite header using `mode=ro`. A database counts as `sqlite_databases_checked` only when `PRAGMA quick_check` actually returns exactly `ok`. The VM's Python SQLite cannot register SiYuan's application-specific FTS5 tokenizer. This produced the real error `no such tokenizer: siyuan` during preparation; it prevents that host runtime from completing the check even though the application's own SQLite supports the tokenizer.

That one exact error is recorded as `unsupported_custom_tokenizer` only after the database schema confirms an FTS5 virtual-table declaration using the `siyuan` tokenizer. It is **not** counted as a passed quick check; the evidence explicitly records `unsupported_custom_tokenizer_quick_check_passed: false`. Other SQLite errors and any non-`ok` quick-check result still fail acceptance. Files without the plaintext SQLite header are counted as `non_plaintext_databases_not_checked`; their header alone does not establish that they are encrypted or healthy.

Runtime SQL/index and document API checks supply separate evidence, alongside the full original note and attachment SHA256 comparisons. They do not turn an unsupported host quick check into a database integrity claim. Neither a local snapshot nor a passed smoke test proves every feature or a complete remote sync round trip.

## Independent image OCR evidence

`image-ocr-probe.py` can test the pulled image while the old service is running. It reads the private `image-before-deploy.json`, inspects that exact local image ID and its pinned source/version labels, and uses the SHA256-verified synthetic PNG from `ocr-worker-smoke.py`. It starts a uniquely named container with `--pull never`, `--network none` and `/bin/sh` as its entrypoint, without a workspace or other mounts and without starting the kernel. Images declaring anonymous volumes are rejected. Only the synthetic image is written under container `/tmp`; worker JSON is supplied through stdin.

The inner BusyBox timeout kills the worker after 115 seconds, and the outer Docker client timeout is 120 seconds. Cleanup checks the random ownership label, container name and image identity before removing only that probe's exact container ID. Default limits are 768 MiB memory and one CPU. Results are written to private `image-ocr-evidence.json`, bound to the image ID.

The VM run reported `passed: true`, `synthetic_text_recognized: true`, `no_mounts: true`, `network_disabled: true` and `probe_container_cleaned: true`, with elapsed time of 1.94 seconds. It recognized the synthetic text `SiYuan OCR 123`. This proves the native worker can load the packaged model and perform inference in the fixed image; it does not exercise the HTTP OCR API, production documents or the current candidate's configuration. The accompanying `test_image_ocr_probe.py` covers command isolation, timeout cleanup, ownership mismatch, declared-volume rejection and recognition failure using a fake Docker runner.

Keep the old workspace, container and private snapshot after success. Any later rollback must account for notes created since the upgrade and changes already synchronized to remote storage.

The operational scripts are retained in `ops/2026-10-12-alpha9`. `browser-smoke-local.py` runs on the operator's machine with Python Paramiko and Playwright, using an existing verified SSH host key and a password supplied through `SIYUAN_TASK_SSH_PASSWORD` for that process. It retrieves the existing access code in memory, does not save browser storage or note content, and emits only a small validation summary. Other scripts run in the private VM stage. `smoke.py` expects that stage's private `index-baseline.json`, collected from the old kernel before the migration, so its document-count assertion uses the real original index.
